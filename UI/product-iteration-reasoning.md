# 产品迭代需求分析：从业务意图到设计决定

## 1. 用途

本参考用于在阅读 PRD、版本记录、产品原型、UI 设计和 UAT 页面后，判断产品为什么变化、运营实际管理什么、操作影响哪里，以及哪些信息可以进入最终设计。

它是页面设计的前置步骤。不要先从原型外观推断需求，再用组件把画面拼完整；应先建立业务对象和状态，再选择页面模式与组件。

本参考吸收了“分析后台产品迭代需求”任务中对运营后台 1.0 至 1.3 的总结。完整案例材料位于工作区根目录的 `运营后台产品演进与设计理解.md`。本文只保留可复用的方法和当前已确认的业务基线。

## 2. 先建立需求推理链

每个新需求依次回答以下问题：

1. **为什么改**：当前业务问题、旧流程限制、用户成本和业务期望是什么。
2. **谁在使用**：运营、管理员、审核人员、客户端用户或其他角色分别能看和能改什么。
3. **管理什么对象**：场景、页面、组件实例、策略、策略组、血缘、人群、内容或日志之间如何关联。
4. **改了什么**：与上一版本相比，哪些能力保留、新增、替换、取消、改为只读或延后。
5. **在哪里操作**：入口、下钻、返回、跨工作区跳转和当前上下文如何保持。
6. **何时生效**：保存、发布、后台配置就绪、客户端接入、缓存刷新和数据可评估是否为不同阶段。
7. **如何判断效果**：指标属于页面、组件、策略还是搜索行为，统计对象、时间、血缘和口径是什么。
8. **风险是什么**：操作是否影响已运行策略、引用关系、下级对象、客户端兜底或历史审计。

这八项未完成前，不把页面外观当成需求结论。

## 3. 证据分工与冲突处理

| 证据 | 主要回答 | 不能单独证明 |
| --- | --- | --- |
| PRD 与修订记录 | 业务背景、范围、对象规则、版本变化和目标 | 最终视觉、当前是否已上线、目标是否达成 |
| 产品原型 | 入口、流程、操作意图、页面间关系和主要状态 | 完整规则、最终尺寸、真实权限和数据 |
| UI 设计 | 信息层级、布局、组件规格、视觉和交互表达 | 后端能力已接入、真实数据正确 |
| UAT/线上实现 | 当前账号下可见的真实行为、数据形态和实现限制 | 最新 PRD 全部交付、其他权限角色一致、业务目标已达成 |
| 接口与埋点定义 | 字段、状态、校验、指标公式和数据边界 | 页面应该如何组织和呈现 |

冲突处理规则：

- 先确认材料所属产品阶段、修订日期和交付范围。产品版本、文档修订号和发布日期不是同一个概念。
- 同一文档冲突时，具体功能章节和最新变更记录通常比开篇摘要更接近当前规则，但仍需记录差异。
- 评论可以提示后续变化或争议，不能自动覆盖正式正文和接口契约。
- UI 与原型冲突时，业务流程按确认后的当前需求，视觉与组件按已确认 UI 规范。
- UAT 与 PRD 冲突时，将其标记为“实现差异”或“版本边界”，不要把偶然实现固化成规范。
- 对象关系、生效、删除、兜底、权限和统计口径的冲突必须进入待产品确认表。

建议维护一张证据矩阵：

| 主题 | PRD 规则 | 原型表达 | UI 决定 | UAT 观察 | 最终设计决定 | 待确认 |
| --- | --- | --- | --- | --- | --- | --- |
| 示例：组件删除 | 删除前检查引用 | 二次确认 | 宽确认层 | 当前未验证 | 展示受影响策略 | 归档时点 |

## 4. 当前运营后台的业务演进基线

现有材料表明，运营后台并非普通数据后台，而是在从“配置运营内容”发展为“围绕用户页面持续优化分发效果”的工作平台。

| 阶段 | 主要业务问题 | 核心能力变化 | 设计含义 |
| --- | --- | --- | --- |
| 1.0 | 配置分散、策略冲突、效果依赖人工复盘 | 建立策略、策略组和可视化运营入口 | 形成对象选择、策略编排和效果查看的基础闭环 |
| 1.1 | 覆盖业务线有限，缺少效果数据 | 扩展业务线，补充曝光、点击与 CTR | 增加业务范围、资源位和数据口径 |
| 1.2 | 页面调整依赖发版，结构与内容耦合 | 引入页面装修，组件承载策略，内容按人群分支 | 分离结构编辑与内容编辑，明确血缘和作用域 |
| 1.3 | 游戏增多后查找困难、内容曝光不足 | 增加场景搜索、横滑和个性化推荐等能力 | 增加场景级组件链、派生结果页和引用型配置 |

稳定的长期目标有三项：提高运营调整效率、降低用户寻找内容的成本、让效果可以被评估。PRD 中的增长数字属于目标，不得写成已实现结论。

## 5. 对象模型与作用域

当前需要同时支持两条配置链：

- `页面 → 页面组件实例 → 策略`
- `场景 → 场景级组件实例 → 策略`

策略的挂载点是组件实例。页面策略组只能编入该页面作用域内的策略；场景策略组只能编入该场景下场景级组件的策略。两种作用域不能因界面长得相似而混编。

| 对象 | 关键判断 |
| --- | --- |
| 场景 | 定义运营范围和跨页面常驻能力的归属，不以当前页面替代 |
| 页面 | 可装修的页面配置；选择、装修、指标和组件列表必须使用同一页面 ID |
| 组件实例 | 页面或场景中的具体模块；联动使用实例 ID，不能只按 `Banner` 等显示名匹配 |
| 策略 | 人群、时机、组件和内容的组合；Where 由入口确定时保持只读 |
| 策略组 | 同一作用域内的执行容器；需解释执行方式、时间覆盖、去重和兜底 |
| 血缘 | 产品与客户端范围；配置、查询、指标与发布均需保留该身份 |
| 人群标签与标签值 | 用于 Who 和内容分支，区别于游戏内容标签 |
| 内容标签 | 用于 What，从内容源系统引用，不等同于用户标签 |
| 预览标签 | 改变预览上下文，不自动等同于策略中保存的 Who |

“场景、页面、血缘、预览人群、当前组件实例”共同组成当前运营上下文。任何一项变化时，都要定义哪些选择保留、哪些清空，以及右侧数据是否需要重新加载。

## 6. 分开结构编辑、内容编辑和只读透视

三类任务不能共用一个泛化的编辑弹窗：

### 页面装修

- 管理组件增减、顺序、显示、布局、尺寸和结构属性。
- 使用完整编辑工作区，并保留中间预览。
- 删除组件时检查挂载策略和引用；说明取消、保存、归档与客户端生效的时点。

### 策略中心

- 管理名称、描述、Who、When、只读 Where 和按组件类型变化的 What。
- 使用宽上下文工作区，保留当前组件与手机预览。
- 默认内容、标签值分支、失效值清理、复制和编组属于业务行为，不只是表单样式。

### 运营管理后台

- 主要用于检索、只读查看配置关系和审计。
- 复用字段定义和表格组件，但不能因此自动增加新增、编辑和删除。
- 素材或内容修改应返回其真相源系统，界面只说明来源和可覆盖范围。

## 7. 配置状态与运行状态必须分离

至少区分以下状态：

1. 草稿或未保存。
2. 后台配置已保存。
3. 已发布或已提交执行。
4. 客户端能力已接入并读取配置。
5. 缓存或同步完成。
6. 当前时间、人群和规则命中，正在运行。
7. 已产生可评估数据。

因此：

- “已配置”不等于“运行中”。
- “后台入口可用”不等于“客户端已经展示”。
- “保存成功”不等于“立即生效”。
- “有指标卡”不等于数据口径已经正确或目标已经达成。

设计中按任务需要展示版本范围、发布时间、预计刷新、生效条件或未接入提示。不要用一个笼统的“成功”状态覆盖整条链路。

## 8. 数据层级与决策用途

| 数据层 | 回答的问题 | 示例 |
| --- | --- | --- |
| 页面 | 整体页面表现怎样 | PV、UV、停留时长 |
| 组件实例 | 哪个模块表现异常或值得优化 | 曝光、点击、CTR、组件特有动作 |
| 策略 | 当前配置和执行情况怎样 | 状态、命中、所属组、内容摘要 |
| 搜索行为 | 用户如何发现内容 | Apply、组合点击、进入游戏率、空结果 |

每张数据卡至少明确对象身份、统计时间、血缘、指标口径和下一步入口。零值、无数据、未配置、未运行和数据失败必须分别表达。

场景级组件跨页面常驻，不能未经确认直接沿用页面组件的分母或流量占比。登录与未登录用户的统计范围也应按当前版本埋点定义，不沿用旧口径。

## 9. 需求变化分类

分析新版需求时，为每项能力标记一种变化类型：

- **保留**：业务规则和入口不变，仅复用既有组件。
- **新增**：新对象、新状态或新操作，需要补充流程和异常。
- **替换**：旧入口或旧规则被新能力接管，需要迁移与兼容说明。
- **取消**：不再交付的字段或操作，应从设计删除，不因旧截图继续保留。
- **只读**：可查看不可编辑，需明确来源系统。
- **未来能力**：模型上允许但本期不可操作，不提前画成可点击入口。
- **实现差异**：UAT 与当前需求不一致，单独记录，不作为新规范。

这项分类应体现在页面方案中，避免把所有历史能力累积到同一画面。

## 10. 风险操作与影响确认

下列操作需要显式确认影响范围：

- 删除页面或组件。
- 删除、停用或移动已运行策略。
- 修改策略组继承、时间、执行方式、去重或兜底。
- 整表覆盖导入、批量替换或清空内容。
- 切换血缘、作用域或来源系统。
- 修改会使客户端回落默认内容的规则。

确认信息至少包含：当前对象、受影响下级或引用、影响的血缘/页面/组件、何时生效、是否可恢复、失败后的原状态是否保留。

## 12. 验收清单

- [ ] 页面能说明业务为什么迭代，而不只复述功能列表。
- [ ] 当前管理对象有稳定 ID、归属和作用域。
- [ ] 场景链与页面链没有混用。
- [ ] 结构编辑、内容编辑和只读透视职责清楚。
- [ ] 保存、发布、客户端接入、运行和数据可评估没有混成一个状态。
- [ ] 页面、组件、策略和搜索指标没有混成一个层级。
- [ ] 历史取消项和未来能力没有被误画成当前可用功能。
- [ ] PRD、原型、UI 和 UAT 的差异已记录并形成设计决定。
- [ ] 高风险操作展示影响对象、时点与恢复方式。
- [ ] 待确认项会改变业务规则或页面架构，而不是普通视觉偏好。
