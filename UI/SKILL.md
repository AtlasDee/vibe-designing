# 运营后台原型设计

将新需求纳入现有运营后台的设计语言，优先组合既有模式，只在新业务明确需要时扩展组件。

## 必读参考

- 收到 PRD、迭代说明、版本对比或新的产品原型时，先读 [references/product-iteration-reasoning.md](references/product-iteration-reasoning.md)，先确定业务目标、对象作用域、版本边界和生效链路，再开始画页面。
- 任何页面设计都先读 [references/ops-center-patterns.md](references/ops-center-patterns.md)，以便使用正确的页面框架、组件、密度和状态。
- 需要判断页面原型、字段组合或对齐旧页面时，再读 [references/page-archetypes.md](references/page-archetypes.md)。
- 分析首页、手机预览、AI 助手 对话，或比较“原型 → UI → 线上实现”时，读取 [references/operations-home-workbench.md](references/operations-home-workbench.md)。
- 分析 Home 下的 Game/频道场景、已装修页面、页面数据总览、组件列表和组件下钻时，读取 [references/game-scene-page-analytics.md](references/game-scene-page-analytics.md)。
- 分析从组件新建、复制或编辑策略的侧边工作区，以及策略页签、人群/时机/内容配置时，读取 [references/strategy-editor-drawer.md](references/strategy-editor-drawer.md)。

## 证据优先级

同时出现需求文档、产品原型、UI 设计和线上页面时，先区分职责，不把任一版本机械复制到另一版本：

1. 需求文档解释业务问题、目标、对象关系、规则、范围和版本变化。
2. 产品原型定义入口、主要流程、操作意图和异常路径。
3. UI 设计定义最终布局、视觉层级、组件规格和对齐关系。
4. 线上实现验证真实账号、配置、权限、数据形态和当前已落地行为，但不自动代表最新需求或效果目标已经达成。
5. 出现冲突时建立差异表，优先采用最新、最具体且与当前版本范围一致的规则；涉及对象关系、生效、删除、兜底和指标口径时必须标记待确认，不能凭视觉稿补写业务结论。

## 工作方式

1. 先回答“为什么迭代”：记录当前业务问题、目标角色、目标指标、旧流程限制和本期不做什么。目标数字只能作为期望，不能当作线上已实现结果。
2. 再回答“运营在管理什么”：建立场景、页面、组件实例、策略、策略组、血缘、人群与内容来源的对象图，明确对象 ID、归属、作用域和来源系统。
3. 标出本轮变化：按保留、新增、替换、取消、只读、未来能力分类，并区分后台配置就绪、发布完成、客户端接入和数据可评估四种状态。
4. 从需求中提取用户角色、入口与返回路径、查询条件、列表字段、操作权限、字段依赖、验证规则、保存与生效、指标口径、异常状态和风险影响。信息不足时先做可逆默认，只询问会改变对象关系或页面架构的问题。
5. 将页面归入运营工作台、页面装修、策略编辑、只读透视、CRUD 管理、权限配置、日志查询或接入/配置之一；复合页面保持一个主任务，其他能力作为局部模块。
6. 把业务状态映射到现有组件。简单主数据使用弹窗；策略使用宽上下文工作区；页面装修使用完整编辑工作区；只读审计页不得因复用表格而擅自增加增删改。
7. 为每个可操作元素定义显示、禁用、成功、失败、权限、未保存和影响确认。删除、停用、解绑、覆盖导入等高风险操作必须说明影响对象与生效时点。
8. 最后检查默认、加载、空、错误、无权限、部分配置、配置未生效、长文本和狭屏状态，并输出需求依据、设计决定和待产品确认项。

## 运营后台首页工作台

首页采用稳定的三段式工作区：左侧业务导航、中间手机内容预览、右侧 AI 助手 上下文数据区。核心闭环是“选择场景或手机模块 → 明确当前对象 → 右侧展示对应数据与运营动作”。

- 顶部导航负责一级产品域，并保持“运营后台”为当前项。
- 左侧导航负责运营后台内部模块与层级，不与手机内的页面导航混用。
- 手机必须在预览区域水平居中；它是可交互选择器，不是装饰图。
- 右侧顶部始终保留面包屑，并与左侧选择、手机选中态和对话内容同步。
- 首次进入展示 AI 助手 问候，再展示可配置的场景选择按钮。
- 右侧底部固定保留禁用态 AI 输入栏与发送按钮，文案为“AI 功能开发中，敬请期待”。
- 场景按钮数量、名称和新旧顺序来自配置；不要把原型中的四项或线上页面中的三项写死。

具体尺寸、状态机、文案规则和验收清单见 [references/operations-home-workbench.md](references/operations-home-workbench.md)。

## Game 场景页面运营

用户进入 Game 场景并选择已装修的页面或标签后，中间手机加载该配置对应的模块，右侧从通用场景引导切换为当前页面的运营总览。

- 页面/标签切换、手机模块顺序、面包屑、问候文案和右侧数据使用同一个当前对象 ID。
- `PV`、`UV`、`停留时长`属于页面指标；组件计数和组件明细属于组件列表，不混成同一级指标。
- 组件总数、已配置策略组件、未配置策略组件和运营策略数卡片同时承担统计与筛选功能。
- 组件明细默认展示前三条；超过三条提供展开全部和收起，筛选变化后恢复收起态。
- 点击手机模块或组件明细进入同一个组件上下文；手机选中态和面包屑同步下钻。
- 原型中的页面 Tab 与手机内的人群标签是不同对象；遇到类似 `slot-demo演示` 的名称时，先确认其业务 ID 和对象类型，再决定控件及联动。

详细对象模型、页面顺序、卡片规格和转化规则见 [references/game-scene-page-analytics.md](references/game-scene-page-analytics.md)。

## 策略编辑工作区

从已选组件点击“新建策略”时，使用覆盖右侧主工作区的大型上下文抽屉，不使用普通居中弹窗。抽屉完整保留顶部导航，并在左侧露出手机和当前组件高亮，帮助用户持续确认策略作用对象。

- 策略名称显示为可关闭页签；页签是独立草稿，不是筛选标签。
- 页签过多时使用 `More` 收纳溢出项，复制和新增保持为独立图标按钮。
- 顶部同时提供“提交”和“提交并编组”，默认只作用于当前活动策略；若产品需要批量提交，必须显式说明范围。
- 名称与描述使用双列表单；名称必填，描述可选。
- 人群、时机、内容使用可进入下一级的摘要选择卡；从组件发起时，“组件”只读锁定为当前组件。
- 切换页签、返回、关闭或删除未保存策略前，保留草稿或提示丢弃。
- 策略抽屉覆盖 AI 助手 区和底部 AI 输入栏；不要在抽屉内重复放置 AI 输入栏。

详细尺寸、状态、交互和原型到设计的修改依据见 [references/strategy-editor-drawer.md](references/strategy-editor-drawer.md)。

## 设计决策

- 保持业务后台的紧凑与可扫读性：不做大型英雄区、营销型卡片或装饰性图形。
- 查询和主操作只保留任务所需的最少内容；不把低频条件常驻在首屏。
- 表格是管理页的主体。列数较多时，优先保留标识、状态、关键归属和操作列，次要内容进入详情、列显隐或水平滚动。
- 状态使用文字和颜色双重表达，不仅依赖颜色。危险色只用于破坏性操作和错误。
- 编辑状态与查看状态要清晰区分；审计日志默认为只读，不增加无业务依据的修改操作。
- 复用现有术语和字段顺序。中英文名称并存时，使用独立字段，不合并成一个自由输入框。

## Figma 交付

当用户要求直接创建或更新 Figma：

- 先使用当前环境的 Figma 生成页面工作流，并在写入前加载对应的 Figma 技能指南。
- 有目标文件或链接时在原文件中新增或更新页面；用户明确要新文件时才创建新文件。
- 先检索已有变量、样式、组件和 Code Connect 映射。有库组件时必须实例化复用；缺失时才创建本地组件。
- 使用 Auto Layout、变量绑定和组件变体，保留可编辑文字，不把主界面扁平化成图片。
- 至少完成一个默认页、一个关键弹窗/抽屉和需求明确涉及的特殊状态。核心交互需用原型连线或清晰注释表达。
- 完成后检查约束、溢出、遮挡、文字截断、固定列和弹窗层级，并通过截图或节点检查确认最终效果。

## 响应格式

交付原型方案时，简要说明：页面原型、信息架构、核心交互、权限/状态差异、待产品确认项。已完成 Figma 时，返回文件或节点链接，并说明创建了哪些页面与状态。
